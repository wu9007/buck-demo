## Business CI/CD Gate

Business repositories must establish CI/CD from the Buck release bundle before they are treated as development-ready.

- Secret and environment variables follow `docs/buck/<version>/secret-environment-governance.md`. For local development, copy `docs/buck/<version>/templates/local-secrets.env.example` to a repo-external private file such as `~/.brick/<repo-name>/local-secrets.env` with directory mode `700` and file mode `600`, or to an explicitly ignored private env file when the business repository already standardizes one. Do not commit real values.
- Business credentials come from GitHub Actions secrets, K8s Secret, config center, or the team password manager. Record only variable names, source category, `SET/MISSING` status, commands, log paths, pipeline/job links, and verification results in issues, MRs, logs, screenshots, and docs.
- Business agents must not read, request, or depend on a Buck maintainer's local secret file such as `~/.brick/brick-next/local-secrets.env`; every business repository owns its own secret source and template.
- Copy `docs/buck/<version>/templates/github-actions.yml` to the repository root as `.github/workflows/ci.yml`. With `frontend/` + `backend/` layout, verify uses `npm ci --prefix frontend`, root `npm run check`, and `./gradlew :backend:test`; do not run root `npm ci`. See `business-ci-cd.md`.
- Copy `docs/buck/<version>/templates/docker/backend/*` to `backend/docker/` and `docs/buck/<version>/templates/docker/frontend/*` to `frontend/docker/`, then adjust only project parameters such as service ports, ingress names, resource requests, and Spring profile.
- Reuse GitHub Actions secrets/variables for `FS_URL`, `REGISTRY_URL`, `DOCKER_USER`, `DOCKER_PASS`, `NAMESPACE`, optional Nexus credentials, and npm registry credentials. Do not commit secrets.
- Before copying the template, identify the actual GitHub Actions runner executor. Shell executor ignores `image` and `services`; if the host Java/Gradle cannot satisfy JDK17 builds, use release-bundle Docker fallback variables such as `CI_BACKEND_VERIFY_IN_DOCKER`, `CI_BACKEND_BUILD_IN_DOCKER`, `CI_BACKEND_TEST_IMAGE`, `CI_BACKEND_BUILD_IMAGE`, and `CI_POSTGRES_IMAGE`. Prefer architecture-verified JDK17 images, for example `eclipse-temurin:17-jdk`.
- If the runner cannot access `services.gradle.org`, configure the business repository Gradle wrapper distribution URL to an internal or otherwise reachable Gradle distribution mirror instead of letting CI repeatedly time out.
- The `DEV_DEPLOY_BRANCH` pipeline should verify, build backend/frontend images, push them to the group registry path, and automatically deploy to `${NAMESPACE}-dev` K8s. `DEV_DEPLOY_BRANCH` is always `dev`. Do not set it to `main`, and do not treat `main` as the development or upgrade baseline.
- The `TEST_DEPLOY_BRANCH` pipeline must verify, build backend/frontend images, push them to the group registry path, and automatically deploy to `${NAMESPACE}-test` K8s for testers. It must use an independent namespace, independent K8s Secret, independent `BUSINESS_TEST_DB_URL` / `BUSINESS_TEST_DB_USERNAME` / `BUSINESS_TEST_DB_PASSWORD`, and a `*.example.com` domain. `BRICK_TOKEN_SECRET` may be shared by product consensus; `BRICK_IAM_ADMIN_INITIAL_PASSWORD` is not a required CI/CD variable unless the business product owner explicitly overrides IAM bootstrap behavior.
- Tag pipelines should verify, build backend/frontend deliverables, and upload them to GitHub Release assets through `${FS_URL}/${release_group}/${GITHUB_REF_NAME}`. Backend tag artifacts must include the executable jar, `version.txt`, non-local yml configuration files, `logback-spring.xml`, and compatibility `logback.xml`; frontend tag artifacts must include the frontend tarball and `version.txt`. Do not publish `*-local.yml`.
- Production frontend Nginx must proxy `/transport/**`, `/brick/**`, and `/api/**` to the backend service. The release template strips `/api` before proxying, so backend controllers still use real business paths without `/api`.
- Keep build artifacts wired through image, deploy, and release jobs. Frontend image jobs should extract `frontend/build/brick/frontend/*.tar.gz` and must not assume `frontend/dist` survives from a previous job.
- Keep CI verification data, dev runtime data, and test runtime data separated. Runtime database and token secrets are injected through GitHub Actions secrets into K8s Secret or precreated environment Secret; do not commit runtime credentials. DNS registration must follow `business-ci-cd.md` and use the business-owned DNS API from `CI_DEV_DNS_API_BASE`.
- Publishing and deployment must remain after `verify_brick_rules`, backend tests, and frontend checks. Do not delete `verify_brick_rules`, mark verification jobs manual, weaken the rule script, or let tag publish/dev/test deploy bypass failed verification.
- Keep `verify_brick_rules` in the `policy` stage, and do not set `if: false` or `continue-on-error: true`.
- If runner variables, K8s permissions, GitHub Release upload, Docker build, or the generated template cannot support the business repository, report the missing environment or create a Chinese brick-next issue. Do not solve it by building a second long-term pipeline convention in the business repository.
