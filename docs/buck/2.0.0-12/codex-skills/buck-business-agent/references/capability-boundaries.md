# capability boundaries

Load this reference only when the current phase needs it. `SKILL.md` remains the hot entrypoint.

## Buck Capability Boundaries

- Query, filtering, pagination, and sorting use `core:query`; page/API list endpoints use `BrickQueryDefinition`, `QueryCriteria`, and `BrickQueryExecutor`.
- Internal exact reads by primary key, unique key, or fixed foreign key may use MyBatis-Plus `selectById`, `selectOne`, or fixed `eq` queries. If a Controller/Service uses a wrapper with `like`, `orderBy`, `selectPage`, handwritten page/size, or frontend-controlled filters/sort, treat it as a Buck boundary violation and refactor to `core:query`.
- Select, radio, multi-select, tag, and enum options use `core:option`, `BrickOptionProvider`, and `@wildbuck/core-option-frontend`. Do not hardcode static `<el-option>` entries or local `xxxOptions = [{ label, value }]` arrays in Vue pages.
- Authentication uses `core:authentication`.
- Authorization, current principal, and permissions use `core:authorization`.
- Business-private anonymous, authenticated-only, or permission rules use `BrickAuthorizationRuleContributor`; path patterns support `{id}` for one segment and `**` for multiple path segments, for example `BrickAuthorizationRule.anonymous("POST", "/openapi/face/**")`.
- User, employee, organization, role, menu, permission, and session governance use `modules:iam`.
- External identity sources, federated login, directory sync, and linking external subjects to local employees use `modules:identity-federation` (`released-candidate`; production default wait for `released`). Do not rebuild those slices inside IAM. Login-entry allowlists stay in `modules:security-setting`.
- EMAIL/SMTP provider settings and formal mail channel governance use `modules:notification-setting`.
- When IAM is adopted, the initial operator account, operator role, registered function/permission/menu catalogs, operator-role permissions, root organization, and operator employee profile are initialized by IAM bootstrap. Menus are visible through `role_permission -> permission -> function_point -> menu`, not by assigning menus directly to roles. Existing menus then become runtime governance data: menu management owns menu name, hierarchy, icon, sort order, and enabled state, and later restarts must not overwrite those values. The built-in operator graph is owned by the IAM module itself; business repositories should not redefine root-organization names, employee names, employee IDs, role IDs, usernames, or similar seed master data in application properties. Configure only runtime controls such as bootstrap enablement and initial password; do not write IAM user, role, organization, employee, permission, or menu initialization scripts in the business repository.
- IAM 登录失败排查时，先读取当前业务仓库采用的 `docs/buck/<version>/` 资料包和 IAM bootstrap 文档，以当前 Buck 资料包默认账号 `operator` 为准；默认初始密码是 `ChangeMe123!`，只有 `brick.iam.bootstrap.admin.initial-password` 可作为业务运行配置覆盖初始密码。旧业务文档或旧 IAM bootstrap 主数据配置（例如 `super-admin`、`BRICK_IAM_ADMIN_USERNAME`、`BRICK_IAM_ROOT_ORGANIZATION_*`、`brick.iam.bootstrap.admin.principal-id`、`username`、`role-id`、`role-name`、`employee.*`）不得优先于当前资料包和数据库事实；发现后把它们标记为业务仓库待清理项。
- Login security, password policy, weak password, MFA policy, and transport security settings use `modules:security-setting`.
- Transport envelope and request digest use `core:transport`.
- Production troubleshooting traceId, MDC, response `trace-id` header, and request completion logging use `core:observability`. Business Logback configuration should start from the release bundle `templates/backend-minimal/src/main/resources/logback-spring.xml`, keep `%X{traceId}` in the main log pattern, and avoid the historical `%X{logRequestId}` key. Business code may read `BrickTraceContext.currentTraceId()` when it needs the current trace id for logs, but it must not log request or response bodies.
- Browser startup public runtime metadata uses `core:client-meta` and `@wildbuck/core-client-meta-frontend`. Business shells read `/brick/client-meta` and let Buck frontend packages bootstrap from it. Do not create a local client meta endpoint, config center, or frontend startup protocol; do not return secrets, tokens, connection strings, internal policy plaintext, request bodies, form content, or plaintext business objects. `/transport/meta` remains the transport-security preflight compatibility endpoint.
- Product usage events use `core:usage-event` and `@wildbuck/core-usage-event-frontend`, bootstrapped from `client-meta` by default. Module-level frontend events should use `createModuleUsageTracker()` with a stable matrix, then `trackPage`, `trackOpen`, `trackAction(featureKey, actionCode, asyncFn)`, or `trackActionResult(featureKey, actionCode, result)` when the action outcome is already known (`SUCCESS`, `FAILURE`, `CANCELLED`, or `ABANDONED`) so pages do not hand-build payloads or duplicate success/failure wrapper branches. For backend-only action outcomes, construct events with `BrickUsageEvents.action()` and publish them explicitly through `BrickUsageEventPublisher`; do not hand-build long records in normal business code or duplicate the same semantic event from frontend and backend. Keep usage-event enabled only when product analysis is required, use stable code dimensions, keep the collect endpoint behind the business authentication/authorization/gateway/transport security chain, route usage events by logger or marker (`io.github.wu9007.buck.usage` / `BRICK_USAGE_EVENT`) in the host logging configuration, and do not collect names, phone numbers, ID cards, tokens, passwords, keys, request bodies, form content, attachments, or plaintext business objects.
- Persistence code uses contract, MyBatis-Plus, migrations, and `core:orm-plus`; do not handwrite SQL or use direct JDBC in business runtime code. Business tables must have exactly one `string(20)` primary key, and production DO/entity classes must use `@TableId(value = "...", type = IdType.ASSIGN_ID)` with a `String` field. If a fixed ID is required, set it before insert instead of switching to `IdType.INPUT`. On soft-delete tables, business unique indexes must include `data_status`, because Buck logical delete keeps the deleted row.
- If ORM Plus metadata seems repetitive, prefer the Buck 1.0.0-41+ lightweight rule: keep MyBatis-Plus physical mapping as the source of truth, add Buck annotations only for Buck-specific audit/sensitive/signature/structure metadata, and file a brick-next issue if the release bundle in the business repository documents a conflicting older rule.
- Audit publishing uses `core:audit`; audit storage and query should use `modules:audit` when adopted.
- OAuth client, scope, OpenAPI action catalog, and machine access governance default to `modules:application-center`.
- Before adopting `core:openapi`, confirm the business authentication model from explicit requirements: OAuth2 client credentials, OAuth2 plus HMAC integrity, or another approved model. Do not enable an extra path just because Buck publishes a capability or an example.
- If the business already owns an organization-access feature that generates `clientId` and `secret` and manages interface authorization, do not force it into `modules:application-center`. For the normal machine-access path, the business feature may own client and authorization data but must expose it through `BrickOAuth2ClientRegistrationResolver`, `BrickOAuth2ClientCredentialsAuthenticator`, and `BrickOAuth2AccessScopeResolver`.
- Use HMAC-SM3 only when the business explicitly requires replay/tamper protection on top of OAuth2 Bearer requests. In that case, supply signing material through `OpenApiHmacIntegrityCredentialProvider`, business secondary integrity checks through `OpenApiHmacIntegrityValidator`, and clustered nonce storage through `OpenApiHmacNonceStore`. Use one `OpenApiAccessLogSink` for OpenAPI call records; it receives Bearer authentication failures, HMAC failures, scope denials, business responses, and business exceptions, so do not create a local authentication-failure filter or access-log model.
- If both `modules:application-center` and a business organization-access feature provide OAuth2 clients or HMAC integrity keys, keep clientId ownership unambiguous through namespaces, provider ownership, or uniqueness constraints. Duplicate `clientId` or multiple-provider matches are Buck integration errors to report or fix, not business-side priority guesses.
- OpenAPI authorization uses `actionId` as the primary authorization key. `method + path` is only for runtime action matching, and business scene codes are secondary business checks.
- Business AI assistants use `modules:ai-assistant` and `core:ai-agent`. `modules:ai-assistant` is currently `maturity: released-candidate` (assembled in Buck Gradle/validation, not the same adoption surface as `released` modules); pilot only with explicit acceptance of contract/API change risk, and keep production default on `released`. Declare assistants through `BrickAiAssistantDefinitionProvider`; declare tools through `BrickAiToolProvider`; execute them through `BrickAiToolExecutor`. Assistant and tool permissions reuse business function permission codes, while `ai-assistant:assistant:manage` is only for assistant configuration governance. The frontend uses `@wildbuck/module-ai-assistant-frontend/shell-entry` as the standard console-shell mount, `@wildbuck/module-ai-assistant-frontend/assistant-panel` only when a custom right-side host already exists, or `@wildbuck/module-ai-assistant-frontend/page-registry` for full pages, and reads available assistants, conversations, model services, and tool-call approvals from the real backend. Tool executors call business services and keep normal authorization, persistence, query, option, audit, and usage-event boundaries.
- External-process agents that need standard MCP `tools/list` / `tools/call` against the business app adopt `core:mcp` (`buck-core-mcp`, explicit dependency; not on starter by default). Prefer contributing tools with `BrickAiToolProvider` / `BrickAiToolExecutor` (auto-bridged to MCP when ai-agent is present). The bridge applies `BrickAiToolGuard`: tools are filtered by the current subject, and ASK/write tools return `REQUIRES_CONFIRMATION` instead of executing. Use `BrickMcpToolProvider` only when the tool must not enter the AI-assistant tool catalog. MCP host is independent of `modules:ai-assistant` sessions. Keep default `brick.mcp.allow-anonymous=false` (do not copy validation-shell true). Do not build a parallel MCP server, expose admin CRUD as the agent main path, or copy validation-shell anonymous MCP settings into production.
- Governance pages should use released `modules:*` backend artifacts and `@wildbuck/module-*-frontend` package exports.
- If a required foundational capability is missing from Buck, create a Chinese issue in brick-next with the business scenario, gap evidence, expected capability, impact, suggested owner, and verification approach. Do not implement a temporary parallel mechanism in the business repository.
