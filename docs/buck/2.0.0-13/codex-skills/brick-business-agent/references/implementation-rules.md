# implementation rules

Load this reference only when the current phase needs it. `SKILL.md` remains the hot entrypoint.

## Implementation Rules

- Prefer published Buck templates and examples under `docs/buck/<version>/templates/` and `examples/`.
- Keep business logic in the business repository; do not modify the Buck release bundle.
- Keep the release-bundle policy script in CI: `node docs/buck/<version>/rules/check-business-structure.mjs .`.
- Keep the release-bundle CI/CD flow in `.github/workflows/ci.yml`: policy, verify, build, image, deploy, release, and notify stages. The business repository may tune project variables but must not remove dev auto-deploy, test auto-deploy, or tag artifact publishing without business-owner and architecture-owner confirmation.
- When adopting CI/CD, always check runner executor type, JDK17/Gradle distribution reachability, container base image availability, Nginx fixed endpoint proxies, build artifact propagation, K8s runtime Secret injection, and DNS registration behavior before treating the repository as delivery-ready.
- Record business-specific requirements, module decisions, permissions, menus, audit events, external systems, and acceptance commands in `docs/business/`.
- If IAM is adopted, configure only the operator bootstrap initial password and related runtime switches in application configuration or environment variables, especially `brick.iam.bootstrap.admin.initial-password`. Existing operator accounts must not be reset by business startup code, and interactive IAM principals must always have matching employee profiles. When credentials are unclear, resolve in this order: current Buck release bundle default operator graph, allowed `admin.initial-password` override, database `principal_account` plus employee profile evidence, then BCrypt hash verification; do not infer credentials from stale business notes or legacy IAM seed keys.
- The minimal shell (`templates/backend-minimal` / `templates/frontend-minimal`) must not default-enable `modules:ai-assistant` or `@wildbuck/module-ai-assistant-frontend`. Mount `@wildbuck/core-ui-frontend` plus IAM `auth-view` first. Do not copy `validation/security-console` assistant wiring, debug endpoints, or `allow-anonymous=true`.
- When adding a business AI assistant, treat `modules:ai-assistant` as `released-candidate` unless the adopted release bundle and module manifest say `released`. Add the backend dependency `io.github.wu9007:buck-module-ai-assistant-backend`, expose assistants with `BrickAiAssistantDefinitionProvider`, expose tools with `BrickAiToolProvider`, implement tool execution with `BrickAiToolExecutor`, and mount UI through `@wildbuck/module-ai-assistant-frontend/shell-entry` for the standard console shell, `@wildbuck/module-ai-assistant-frontend/assistant-panel` for custom right-side hosts, or `@wildbuck/module-ai-assistant-frontend/page-registry` for full pages. Verify against the real backend and database; frontend mock assistants, mock conversations, mock permissions, or copied validation shell data are preview-only and not acceptance evidence.
- For frontend work, proxy Buck fixed endpoints `/transport/**` and `/brick/**` to the backend. `configureHttp({ baseUrl })` only covers core API requests and does not replace login or transport proxying. Request digest protects configured backend paths; fixed pre-login endpoints such as `/transport/meta`, `/brick/captcha`, `/brick/login`, `/brick/mfa/**`, and `/brick/password/change` must remain reachable before login.
- For authentication flow pages（认证流程页）, choose either default reuse or full-page customization. Default reuse mounts `@wildbuck/module-iam-frontend/auth-view`; full-page customization may replace the UI for the first login factor, captcha, MFA/two-factor page, forced password change, and password reminder, but must reuse `@wildbuck/module-iam-frontend/auth-state`, `@wildbuck/module-iam-frontend/auth-workspace`, or `@wildbuck/core-authentication-frontend`. Send MFA codes through `app.sendMfaVerificationCode()` and let the user enter the received code; do not read or auto-fill debug verification codes. Do not create a local auth request client（不得自建本地认证客户端）, do not deep-import `@wildbuck/module-iam-frontend/src/features/...`, do not reimplement `/brick/login`, `/brick/mfa/**`, or `/brick/password/change`, and do not proxy or call `/debug/**` in business code.
- For session expiration in concurrent frontend requests, configure `@wildbuck/core-api-frontend` once in the business shell with `tokenRefresh` (single-flight `/brick/token/refresh`, persist RT) and `createBrickSessionErrorHandler()` for the **terminal** path after refresh fails. Terminal handling follows `expirationStrategy` from client-meta: `LOGIN_OUT` clears session; `SCREEN_LOCK` soft-suspends (keep URL/drafts) with official recovery UI — never “401 always clearSession” as the only path. Historical `VERIFY_PASS` maps to `SCREEN_LOCK`. Unlock re-issues via `/brick/login` (not step-up `/brick/session/verify-password`); do not auto-replay failed requests. Page-level `catch` blocks must call `isBrickSessionError(error)` and return before showing local “加载失败” messages. Do not copy a local 401 debounce gate into every page.
- With the default release-bundle `/api` rewrite, `/api` is only the frontend proxy prefix. Frontend code calls `request('/face-archives')`, the browser reaches `/api/face-archives`, and the backend Controller maps `/face-archives`; do not add `/api` to Spring controller mappings.
- Before starting frontend debugging, start the real backend first and confirm `BUSINESS_API_BASE_URL` or the default `127.0.0.1:8080` proxy is reachable. A local mock backend must not be used as formal acceptance evidence; do not construct local mock menus, mock permissions, or mock business data in the frontend. IAM menus, permissions, audit logs, OpenAPI, call records, and cleanup configuration must be covered by real backend verification. Temporary visual preview evidence must be labeled as such and must not be reported as real backend verification.
- Use `@wildbuck/core-query-frontend` to build frontend `QueryCriteria` when submitting Buck query DSL. The frontend package does not define field allowlists; backend `BrickQueryDefinition` remains the authority.
- Use `@wildbuck/core-option-frontend` to load options from `BrickOptionProvider` and render them with `v-for`.
- Governance pages must be mounted through released `@wildbuck/module-*-frontend/page-registry` exports. If IAM pages fail to open, run `validateIamPageRegistry()` first and fix route, loader, permission, or menu registration before considering new business code.
- Use Element Plus and Buck console CSS tokens from the release bundle. Do not create an unrelated theme system or hardcode page colors that bypass the shared tokens. Default to the `blue` light theme unless the business owner explicitly wants another theme; `night` is the full dark theme, while `green`, `orange`, and `guard` are dark-sidebar plus light-content brand themes.
- Theme preference vs render token is a hard gate: `system` is a preference only, never a CSS token. Use `createBrickConsoleAppearanceRuntime()` or `resolveBrickConsoleAppearanceTheme()` so `data-theme` and Shell `:theme` bind `resolvedTheme` (`blue`/`orange`/`guard`/`green`/`night`), while `:theme-preference` / save logic may keep `system`. Forbid `data-theme="system"`, `:theme="'system'"`, and business-owned `matchMedia`/`localStorage` theme protocols. Login and authenticated shells must both use resolved tokens. After appearance wiring changes, hard-refresh the frontend and verify “跟随系统” against OS light/dark switches.
- Identity / Authorization / Workspace Profile are three layers. A topbar “工位视图 / 工作台场景” switcher is UI-only (menu focus / default home); it must not change token or call login. Filtered menus must stay within `principal.permissions`. Do not label it as IAM “角色切换” or imply soft-hide is security. Prefer `@wildbuck/core-ui-frontend/workspace-profile` helpers and `BrickWorkspaceProfileSelect` from `shell`; business owns profiles config (not IAM role admin). Details: release-bundle `business-frontend-page-patterns.md` section「Identity、Authorization 与 Workspace Profile」.
- Use `BrickFilterToolbar` from `@wildbuck/core-ui-frontend/patterns` for list-page filter toolbars. It only owns layout and actions; backend query allowlists, operators, sort fields, and page limits still belong to `core:query` and `BrickQueryDefinition`. Do not import page patterns from `@wildbuck/core-ui-frontend/shell`.
- In `BrickFilterToolbar`, every filter field must provide a 中文 placeholder, a visible label, or an explicit `aria-label`; do not rely on Element Plus default text such as `Select`. Chinese admin applications must install Element Plus with `zh-cn` locale in the frontend shell. Multilingual applications need a formal i18n strategy instead of ad hoc English defaults.
- Element Plus `daterange` / `datetimerange` controls inside `BrickFilterToolbar` should put `brick-filter-toolbar__field--range` on the direct grid item so the range field spans two columns and becomes full-width on small screens. If a page wraps the range picker in `el-form-item` or a local field wrapper, put the class on that wrapper instead of writing page-local grid CSS. The toolbar `actions` slot may contain `BrickActionBar`; do not add page-local `.brick-action-bar { padding-top: 0; }` overrides.
- Save forms, configuration forms, and drawer edit forms are formal productization surfaces. Mark editable fields explicitly with `（必填）` or `（选填）`, render only one visible red star for each required field, run `validateBrickRequiredFields` before save, and use `showBrickStatus` for save success/failure. Do not keep save-stage feedback in local bottom error blocks or replace the flow with page-local `ElMessage` warnings.
- Use `BrickImageUploadField` from `@wildbuck/core-ui-frontend/fields` for avatar, menu icon, application logo, face images, certificate images, and shared image resource upload fields. The business page owns the upload API call and resource binding, but must call released `core:file-resource` endpoints or a thin business backend wrapper, not rebuild hidden file inputs, local preview blocks, upload button CSS, or a parallel file storage protocol. Use `BUSINESS_ATTACHMENT` for business attachment images that are not IAM avatars, menu icons, or application logos. If the released component or `core:file-resource` category model cannot cover the business scenario, file a Chinese brick-next issue.
- For editable API keys, app secrets, webhook secrets, SMTP passwords, and similar fields whose plaintext is not returned after save, use `BrickManagedSecretInput` plus `resolveBrickManagedSecretField()` from `@wildbuck/core-ui-frontend/fields`. Drive `configured` from field-level flags such as `appSecretConfigured`, `apiKeyConfigured`, `secretKeyConfigured`, or `credentialMasked`; do not replace it with page-level `configured` or “the whole config exists”. Reuse the helper output for required/optional labels, `validateBrickRequiredFields`, placeholder/hint text, and “leave blank to keep existing secret” semantics instead of building a local `SensitiveCredentialInput` state machine.
- Use `BrickConsoleShell` for sidebar collapse, navigation-group collapse, built-in sidebar menu search, topbar global actions, and the released user menu. Sidebar collapse uses `v-model:sidebar-collapsed`; group collapse uses `v-model:sidebar-collapsed-group-keys`, `sidebar-group-collapsible`, group `defaultCollapsed`, and `collapsible: false`. Menu quick search uses `sidebar-searchable`; add route `keywords/searchKeywords` when titles are not enough. Use `sidebar-nav-before` only for extra filters above the menu. The topbar must be a flat global action bar attached to the browser top edge and sidebar top edge, not a floating card inside the page content. It must not show system information, environment descriptions, menu search, the current active menu title, menu group, or page description; keep it for global actions such as refresh/menu guide/notifications and the current-principal avatar menu. Provide refresh/menu-guide/notification buttons through `topbar-actions`; Buck provides the action area and theme, while the business shell owns the actual refresh, guide, and notification behavior. Put system identity in the sidebar brand area and page context in the sidebar active state and page header. Sidebar menu icons' primary source is IAM menu-management uploaded images (`iconResourceId` → runtime `iconUrl`); render priority is uploaded `iconUrl` > component `icon` > line-icon fallback. String `MenuBindingDescriptor.icon` is not an automatic image resource. `abbr`/`iconText` are search/auxiliary only, not default collapsed primary visuals. Provide collapsed logo through `brand-mark` or documented Shell slots. Do not copy `BrickConsoleSidebar` or build a local Topbar. Executable pages still come from `navigationGroups` and module `brickRoutes` / `page-registry`.
- Formal topbar actions must use Element Plus button semantics or another released public component. Do not place native `<button>` elements, ASCII icon buttons, or page-local ad hoc styling directly in `topbar-actions`.
- Business-side page guides may implement concrete steps locally, but must follow the Buck guide convention from the release bundle: the topbar `topbar-actions` guide button is the entry, target elements use stable `data-guide-id`, steps include `target/title/body/placement`, overlays and buttons reuse Buck tokens and wording, completion keys are scoped by app/user/route, and drawer targets are opened and rendered before positioning. If the release bundle lacks enough guide capability for the business need, file a Chinese brick-next issue instead of creating a different guide pattern.
- Use `BrickConsoleDrawer` from `@wildbuck/core-ui-frontend/shell` for create, edit, and detail side drawers. Short confirmations use `ElDialog`. Do not pass fixed pixel `size` values such as `size="520px"` to the standard drawer; keep the Buck default or a documented responsive exception. Only use raw `ElDrawer` when the release bundle says the scenario is outside `BrickConsoleDrawer`, and record why in business docs. Do not copy `validation/security-console` CSS to chase visual differences; the business UI baseline is the released `@wildbuck/core-ui-frontend` package and `theme.css`.
- Use `BrickActionBar` for formal form/card/drawer bottom actions and keep the standard order `secondary -> primary -> danger`. Use `BrickRiskConfirm` for dangerous confirmation paths such as delete, reset, force-offline, key rotation, or global configuration save; do not ship a mixed confirmation model inside one business page.
- If a page is defined as a formal business capability in `docs/business/requirements.md`, `docs/business/menus.md`, `docs/business/acceptance.md`, or equivalent business docs, it must not ship as a local example-data page, placeholder list page, or mock-record demo. Connect it to the real query/detail/action closure or stop and record the remaining gap explicitly.
- Do not keep local mock backend entrypoints such as `mock:backend`, `mock-backend`, or `frontend/scripts/mock-backend.*` in a business repository. If a temporary preview server is unavoidable, remove it before delivery and keep it out of debugging and acceptance evidence.
- After each clear verified phase, commit and push if the repository rules require it.
